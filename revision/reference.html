The opening and the board (7)

SCRIPTThe 3-minute opening script?
  1. Restate in one sentence: “So we are building X for Y users, and the hard part is Z.” (10 s)
  2. Three clarifying questions, picked from: scale today and in two years · the one latency that matters · read or write heavy · what must never be lost · what is out of scope. Write the answers in the requirements corner as you get them. (90 s)
  3. Name the load-bearing categories aloud and cross out the rest: “This is Compute and Bandwidth; storage and memory are ordinary here.” (15 s)
  4. Say the plan: “I will do requirements and numbers in ten minutes, the design in fifteen, then two deep dives, and I will leave five minutes for failures. Stop me whenever you want to go deeper.” (15 s)
  5. Then start writing; never start drawing before the numbers are on the board.

SCRIPTThe five sentences that carry the interview?
  • “Because X is a requirement, I need Y.”
  • “The alternatives I see are A and B. I prefer A because … The cost of that choice is …”
  • “At 10× this breaks at Z first; here is how I would notice, and here is the mitigation.”
  • “This is a hotspot because …; I would partition by … and accept … as a consequence.”
  • “The failure I worry about most is …; recovery works like …; the blast radius is …”

LAYOUTThe prompt is functional-heavy and the interviewer wants the diagram first. The rule?

This prompt is functional-heavy. The interviewer dictates the requirements, asks for the agent loop and the architecture, and does not want a GPU bill: model infrastructure is out of scope and cost is declared infinite. Numbers cover only what you buy: sandboxes, model calls, storage. On a functional-heavy prompt, say the one numbers line before drawing if nobody objects. If the interviewer asks for the diagram first, draw and put the numbers line right after the diagram. The board below uses the diagram-first order.

  • You drive. The interviewer should rarely need to steer.

≈ 3.15 × 10⁷

SHAPE OF CALCULATIONHow do you compute QPS?

QPS = daily ops / 10⁵; peak = 2-5× average.

SHAPE OF CALCULATIONHow do you compute Bandwidth?

Bandwidth = QPS × payload size (bytes/s → ×8 for bits).

SHAPE OF CALCULATIONHow do you compute Storage/day?

Storage/day = writes/day × object size × replication (or × 1.5 for erasure coding); /year × 365; add index/metadata ~1-5 %.

SHAPE OF CALCULATIONHow do you compute Connections?

Connections = concurrent users × connections each; long-lived (chat, streaming) ≠ request/response.

SHAPE OF CALCULATIONHow do you compute Workers?

Workers = arrival rate × service time (Little’s law: L = λW); add headroom 30-50 %.

SHAPE OF CALCULATIONHow do you compute Cache size?

Cache size = hot fraction (often 20 %) × working set; hit rate you need = 1 − (backend capacity / total load).

SHAPE OF CALCULATIONHow do you compute Partition size?

Partition size = total / target-per-shard (e.g. 50-100 GB per hot shard, 1-2 TB per cold shard).

API shapes (7)

API SHAPEAPI shape: Sync request/response. When, the request and response, and what gets probed?

When. one input, one answer, seconds

Request and response. POST /v1/<verb> {inputs, options} + bearer auth + Idempotency-Key → 200 {id, result, usage, version}; 429 + Retry-After; 4xx validation

What the interviewer probes (say these unasked). retry: same key returns the stored answer, no second charge (24 h record) · timeout: client retries with backoff, server keeps working · long answers: stream tokens (SSE), first token in under a second, max_tokens cap · version: alias by default, pinned version allowed, Deprecation header for 90 days · large inputs by file_id, not inline · request_id in a response header for disputes

API SHAPEAPI shape: Streaming session. When, the request and response, and what gets probed?

When. live data in, results out, state between messages

Request and response. POST /v1/sessions {client_id, model, options} → {session_id, gateway_url, token, expires_at, version}; up {session_id, seq, ts, payload}; down {result_seq, ts, type, payload, version} + control messages

What the interviewer probes (say these unasked). resume: POST /sessions/{id}/resume {token, last_result_seq} inside a grace window (60 s), server resends only results after last_result_seq, nothing replayed, nothing lost · acks: client acks result_seq, server keeps unacked results for the grace window · heartbeat every few seconds, 3 misses = dead · token expires and is renewed over the open socket · control messages down (granted rate, backpressure) · version pinned for the session’s life, never switched mid-stream · explicit close releases quota at once · byte-rate cap per session

API SHAPEAPI shape: Async job. When, the request and response, and what gets probed?

When. minutes to hours of work

Request and response. POST /v1/jobs {file_ids, options, callback_url} + Idempotency-Key → 202 {job_id, state}; GET /jobs/{id} → {state, progress}; GET /jobs/{id}/results?cursor; DELETE /jobs/{id}

What the interviewer probes (say these unasked). same key + same body → same job, same key + other body → 409 · state machine with named states · progress in chunks, partial results pageable as chunks finish · chunk retries with backoff, dead-letter after N, the job reports the failed chunk · webhook signed and retried for 24 h, idempotent on the receiver · results expire (TTL) · priority: jobs run at the lowest weight on spare capacity

API SHAPEAPI shape: Upload. When, the request and response, and what gets probed?

When. bytes larger than a request

Request and response. POST /v1/files → presigned URL + file_id (expires in minutes); multipart PUT ?upload_id&part=N idempotent per part; complete {parts, checksums} → READY

What the interviewer probes (say these unasked). bytes never cross the API servers · checksum per part and at complete · abort cleans incomplete uploads (lifecycle rule) · size and format validated before READY · the file_id is referenced by later calls, never the bytes

API SHAPEAPI shape: Read / list. When, the request and response, and what gets probed?

When. feeds, search, dashboards

Request and response. GET /v1/<thing>?cursor=&limit= filters in the query, tenant from the token never the body → {items, next_cursor, as_of}

What the interviewer probes (say these unasked). keyset cursor, not offset, so inserts do not shift pages · limit capped · as_of or watermark says how stale · ETag / If-None-Match for caching · “seconds stale is fine” said aloud when it is

API SHAPEAPI shape: Write with a guard. When, the request and response, and what gets probed?

When. booking, inventory, money

Request and response. POST ... {resource, amount, version} + Idempotency-Key → 201 or 409 conflict, 402 payment required

What the interviewer probes (say these unasked). optimistic version (If-Match) or a conditional update on the row · holds with TTL and a limited number of extensions · saga with compensation across shards, no 2PC · the retry after a timeout must find the existing record, not create a second

API SHAPEWhich fields always exist in the API?

Fields that always exist: id, created_at, version, request_id header, usage or cost where billing exists, Retry-After on every 429 and 503.

Which store (11)

STOREThe requirement says transactions, money, status machines, metadata with joins. Which store, why, and the nuance?

Store. Postgres, sharded by tenant or listing id past ~1 TB

Why. ACID, unique constraints as guards

The nuance to say. shard key is the one you look up by; read replicas for the read path; hot rows serialize at ~200/s

STOREThe requirement says counters, sessions, locks, rate limits, anything with a TTL. Which store, why, and the nuance?

Store. Redis cluster, shard by key

Why. sub-ms, atomic Lua, TTL cleans up

The nuance to say. not durable: never the booking truth, never the ledger; hot key for the biggest tenant, split it

STOREThe requirement says high write rate, append-only, time-ordered reads. Which store, why, and the nuance?

Store. Cassandra / ScyllaDB, partition by (owner, time bucket)

Why. writes scale, one partition scan per read

The nuance to say. partitions under ~100 MB (add a bucket); no delete-on-ack queues (tombstones), use a flag + TTL; no joins

STOREThe requirement says blobs: video, images, checkpoints, artifacts, archives. Which store, why, and the nuance?

Store. object storage, erasure coded

Why. cheapest durable bytes, presigned access

The nuance to say. lifecycle rules for expiry; listing is eventual; multipart for anything over a few MB

STOREThe requirement says events between services, buffering, replay. Which store, why, and the nuance?

Store. Kafka, partition by the key you aggregate on

Why. absorbs bursts, at-least-once, replay from offset

The nuance to say. order only inside a partition; retention bounds replay; consumer lag is the health signal; hot partition for a hot tenant

STOREThe requirement says full-text or vector search. Which store, why, and the nuance?

Store. inverted index / ANN shards in RAM, document-partitioned, replicated

Why. every query to every shard, merge by raw score

The nuance to say. tail = slowest shard, hedge at p95; delta index for freshness; filters inside the shard

STOREThe requirement says time series, metrics, dashboards. Which store, why, and the nuance?

Store. TSDB with roll-ups

Why. compression, cheap ranges

The nuance to say. cardinality is the limit: pre-aggregate per site or tenant

STOREThe requirement says analytics, disputes, audit over months. Which store, why, and the nuance?

Store. Parquet in object storage (+ ClickHouse for interactive)

Why. immutable, scan when needed

The nuance to say. partition by date and tenant; the ledger is elsewhere, this is evidence

STOREThe requirement says per-user lists, adjacency, timelines. Which store, why, and the nuance?

Store. Redis lists / KV

Why. ids only, O(1) by key

The nuance to say. active users only, rebuild on return; celebrity keys get a near cache

STOREThe requirement says read-heavy hot path. Which store, why, and the nuance?

Store. cache (read-through or cache-aside) + near cache

Why. the cache is the system at 100:1

Pattern. fan-out on write below a threshold, on read above, merge two sorted lists at read

FIVE QUESTIONSThe five questions that generate the nuances for any box?
  1. What is its unit of work, and what does one unit cost? (a request, a frame, a token, a chunk, a byte)
  2. What state does it hold, and for how long? (none → disposable; seconds → ring buffer; a session → sticky with a map; forever → a store with a durability number)
  3. What happens when it dies mid-work? (who notices, in how long, who takes over, what is replayed, what could be duplicated and what id prevents that)
  4. What is its hot key? (the one tenant, celebrity, partition or row that gets all the traffic, and how it is split)
  5. How does it find the others, and what happens when that lookup is stale? (session map, capacity view, config push, CDC; and the TTL or token that bounds the staleness)

Where the bytes go (10)

DATA PATHWhere do the bytes go? The rule to say.

“Queues carry references; bytes live where they are cheapest to keep for as long as they must wait: memory for a second, object storage for minutes or hours. The GPU never waits on a storage round trip for live work.”

DATA PATHSync call: where is the queue, where are the bytes, and which thread touches which counter?

Three kinds of threads, three kinds of state. A request handler is a lightweight task (goroutine, asyncio task), not an OS thread, so one gateway runs tens of thousands of them at once, one per open connection. Each handler owns its connection and its bytes; it is the only thing that touches the money counter in Redis, twice: an estimate at admission (arrow 2) and a settle with the worker’s actual usage at the end (arrow 9), both as atomic Lua scripts because N gateways share the same bucket. The scheduler loop owns the local fairness state (deque lengths, deficit counters, in-flight per host) and never touches Redis. The config watcher receives the controller’s weights and quota-divided-by-N every 5 seconds and swaps them in atomically, so the scheduler reads them without a lock. The bytes never enter the queue; the queue is a list of who waits.

DATA PATHStream: how do frames reach the GPU, and who decides the host?

No queue system in the path: the stream gateway pushes each frame directly to the host that owns the session, and the only queue is a small in-memory buffer inside that host where frames wait for the next batch. The session router decides the host once, at open; the data plane never asks it again.

DATA PATHBatch job: why object storage and Kafka?

Here the bytes are hours of video and may wait for hours, so they live in object storage and Kafka carries only chunk ids; a worker fetches a chunk’s frames when its turn comes, and partial results go back to storage as each chunk finishes.

DATA PATHFair share across many gateways without a shared queue?

Why it adds up without a shared queue: the load balancer gives every gateway the same mix of tenants, so N local 5/3/1 schedulers behave like one global 5/3/1; the controller gives every gateway the same weights and each tenant’s quota divided by N, and moves shares between gateways when the reported usage is skewed. The one case that breaks the picture is a tenant stuck on few gateways (a sticky hash); that tenant is handled by a shared Redis bucket or a central admission service instead.

DATA PATHWhat the controller does, in one line?

gateways report usage every 5 seconds, the controller sums it, splits each quota across gateways in proportion, and pushes the same versioned config to all of them

DATA PATHWho updates which counter? The sentence to say.

Redis holds the money counter, updated by the request handler with an estimate-then-settle pair of atomic scripts. The scheduler holds only local fairness state. The controller refreshes the shares every 5 seconds and the config watcher swaps them in.

DATA PATHInside the model gateway: router and serving process, what to say?

the router is a lookup, the bytes make one gRPC hop from the gateway to the host’s serving process, the host batches whatever is waiting into each GPU step, and streams tokens back on the same connection; capacity flows the other way once a second so the router never sends to a full host.

DATA PATHDoes the scheduler push to the GPU host, or does the worker pull? And if asked why not pull?

Push. The scheduler makes a gRPC call on a pooled, long-lived connection to the serving process on host H and sends the bytes inside the call. The worker never pulls. Pull needs the worker to know which gateway holds work, which means a broker in the middle, and that is the hop you avoid for a sub-second call. Backpressure comes from the host instead: it keeps a bounded queue, rejects fast with RESOURCE_EXHAUSTED when full, and the scheduler retries on another host. That retry is rare because the router’s 1-second capacity view already steered the request away from full hosts. Pull is the right shape in diagram 3, where workers pull chunk ids from Kafka because the wait is long and the bytes sit in object storage.

DATA PATHWhy charge an estimate at admission and settle at completion?

Why the estimate and the settle: it is the card authorization pattern. The gateway must decide admission before the work runs, and nobody knows the output token count until generation ends, so it reserves the worst case (input estimate plus max_output_tokens) and settles to the actual number at the end. Charging nothing until the end would let a tenant launch 1,000 concurrent requests and pass its quota before the first one finished. A reservation carries a TTL of a minute or two, so a gateway crash cannot leave tokens reserved forever, and a reaper reconciles from the Kafka usage events. A tenant that sets a huge max_output_tokens reserves more per call and gets fewer concurrent calls, which is the right incentive.

BOARD 10 · WHOLE BOARDEvaluation and testing harness for LLM coding agents: write the whole board, diagram first.

0-5 min · The agent loop (only if the first prompt is “Build a coding agent”, otherwise these minutes go to requirements)

LOOP     user msg -> context = system prompt + tool schemas + history -> model call (streamed)
         -> tool_use? -> permission check (allow / ask / deny, per tool and per path) -> run tool -> append tool_result -> loop
         -> stop on a final answer, max turns, or user interrupt
TOOLS    read / write / edit file · shell command (compiler, tests) in a sandbox · code search (grep, glob, symbol index) · web fetch
CONTEXT  stable prefix cached (system + tools) · compaction near the window limit: summarize old turns, keep plan + files touched
SESSION  every event appended to a server-side session log (same schema as the harness trajectory)
         laptop -> phone = a thin client reattaches by session_id and tails the live log (Kafka or a hot store) from its last seq
MEDIA    images / audio in -> upload -> file_id in the message · out: text, diffs, Mermaid or image diagrams

5-10 min · Requirements, top-left (accept what is dictated, compress, move)

FR   run a suite: N tasks x agent build x model version -> k samples per task, each try in its own fresh sandbox
     tools against the sandbox: files, shell, compiler and test output, code search · multimodal task inputs
     score each sample: hidden unit tests, compile, LLM judge · compare run A vs run B per task, same suite version
     record the full trajectory (model calls, tool calls, outputs, latency) · replay and debug any try
NFR  one release run = 10,000 agents x up to 100 turns, done in < 30 min (task in -> final score)
     no state survives between tries · deterministic where we control it · control plane 99.99%
     99.99% = Postgres sync replica across 3 AZs · scheduler leader election · Kafka RF 3 · hosts across 3 AZs
     keep everything for replay · hot 30 days, then cold
OUT  model serving, weights, inference engine, GPUs, cost (declared infinite)

  runner + tool broker run OUTSIDE the SBX on the host · tools exec in the SBX over vsock

32-48 min · Two deep dives, annotate the boxes

A isolation + determinism: fresh microVM per try, workspace only · runner and credentials outside · egress = frozen mirror
  pinned toolchain hash, mirror snapshot, repo commit · fixed seed, clock set at boot · destroy at end · host leak checks
  limits: the clock moves after boot, parallel test order, thread scheduling, so tool outputs are recorded, never assumed
  REJECT reused containers with cleanup (caches, /tmp, background processes leak) · REJECT live internet (non-reproducible)
B trajectory + replay: event = (attempt_id, try_no, seq, type, payload or blob hash, content_hash), append-only, deltas
  replay 1 render: read the log, no compute
  replay 2 re-execute: new SBX, model responses served from the log by request hash, tools run for real
    outputs normalized (durations, PIDs, temp paths stripped) before hashing · divergence = first seq whose normalized hash differs
  replay 3 agent-only: recorded tool results too, fully deterministic, for testing a new agent build
  retention hot 30 d / cold 1 yr · task code can be customer code: encrypted, access-logged, never in the analytics rows

48-55 min · Failures and trade-offs, bottom

stuck agent      tool call > 90 s or model call > 60 s · no event 120 s · attempt > 25 min   kill, TIMED_OUT (agent fault, scored fail)
sandbox leak     lease without heartbeat · VMM process, tap device or disk layer outlives lease   reaper destroys, host drained after 3 leaks
model GW 429     429 rate, queue time per turn          backoff + jitter, least-slack-first, short quota: stratified sample, run PARTIAL
poison task      same task fails INFRA 3 times across hosts                                       quarantine, report, run finishes
scheduler crash  leader lease lost    new leader · hosts renew try leases in Postgres · re-lease bumps epoch, stale epoch writes rejected
chose: runner outside SBX · microVM per try · admission to quota · record model + tool outputs · log is truth · INFRA != agent failure

55-60 min · Summary, said not written. “A run is 10,000 samples. Each try gets a fresh microVM workspace restored from a pinned snapshot, while the agent runner stays outside it on the host with the credentials. Every model call and tool call is an append-only event with a sequence number and a content hash, so any try can be re-rendered exactly, or re-executed against its recorded model responses until the first normalized divergence. The 30-minute budget is a per-turn latency budget: up to 100 sequential turns in 25 minutes, so the gateway serves the least-slack agent first and the quota is sized to the natural rate, not the average.”

Shorthand used on this board: SBX = sandbox (one microVM, workspace only) · runner = the trusted agent runner on the host · GW = gateway · idem = idempotency key · seq = per-try event sequence number · epoch = lease fencing token · INFRA = infra error, not the agent’s fault · TPM = tokens per minute · p50 = median latency · LLM judge = a model that grades an output against a rubric.
