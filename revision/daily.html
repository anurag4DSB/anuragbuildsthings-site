The opening and the board (5)

SCRIPTThe 3-minute opening script?
  1. Restate in one sentence: “So we are building X for Y users, and the hard part is Z.” (10 s)
  2. Three clarifying questions, picked from: scale today and in two years · the one latency that matters · read or write heavy · what must never be lost · what is out of scope. Write the answers in the requirements corner as you get them. (90 s)
  3. Name the load-bearing categories aloud and cross out the rest: “This is Compute and Bandwidth; storage and memory are ordinary here.” (15 s)
  4. Say the plan: “I will do requirements and numbers in ten minutes, the design in fifteen, then two deep dives, and I will leave five minutes for failures. Stop me whenever you want to go deeper.” (15 s)
  5. Then start writing; never start drawing before the numbers are on the board.

SCRIPTThe five sentences that carry the interview?
  • “Because X is a requirement, I need Y.”
  • “The alternatives I see are A and B. I prefer A because … The cost of that choice is …”
  • “At 10× this breaks at Z first; here is how I would notice, and here is the mitigation.”
  • “This is a hotspot because …; I would partition by … and accept … as a consequence.”
  • “The failure I worry about most is …; recovery works like …; the blast radius is …”

LAYOUTThe prompt is functional-heavy and the interviewer wants the diagram first. The rule?

This prompt is functional-heavy. The interviewer dictates the requirements, asks for the agent loop and the architecture, and does not want a GPU bill: model infrastructure is out of scope and cost is declared infinite. Numbers cover only what you buy: sandboxes, model calls, storage. On a functional-heavy prompt, say the one numbers line before drawing if nobody objects. If the interviewer asks for the diagram first, draw and put the numbers line right after the diagram. The board below uses the diagram-first order.

Numbers (13)

SIX LINESThe six lines in the room, in four minutes?

In the room: 4 minutes, six lines (objects, egress = constraint, ingress ratio + growth, hot set, capacity vs IOPS check, network). The rest is ammunition for probes.

CATEGORIESThe five estimation categories: the question each answers, its unit, and when it is load-bearing?
Category The question Six-line method line Typical unit When it is load-bearing
Traffic How many operations per second, average and peak, and which operation is the constraint? Line 2, the constraining op/s (from line 1, objects and users) QPS, writes/s, messages/s, frames/s Chat, feeds, gateways, rate limiters, search, payments: anything where a request is the unit of work
Bandwidth How many bytes per second in and out, and what is the ratio? Line 3, egress against ingress; line 6, network ports MB/s, GB/s, Gbps; ports of 10 or 100 GbE Video, media, object storage, backups, checkpoints, log pipelines: anything that moves large blobs
Storage How many bytes total, per day, per year, and on how many devices? Line 3 growth; line 5, capacity against IOPS TB, PB, disks Blob stores, data lakes, archives, event logs kept for audit
Memory What must sit in RAM or SSD to meet latency, and does it fit on one box? Line 4, the hot set GB, TB, nodes Caches, timelines, session maps, indexes, order books, ANN vectors, tries
Compute How many GPUs or cores, when the work per request is heavy? Line 2 again, when the unit is a frame, a token or a match, divided by throughput per device GPUs, cores, tokens/s, frames/s Model serving, transcoding, embedding, training, matching engines

CATEGORIESStep 0, said aloud before any number?

“Before I size anything: this is a Traffic and Memory system, storage and bandwidth are small here, and there is no heavy compute. So I will size the request rate, the hot set, and check that the hot set fits in RAM on a handful of nodes.” Then the six lines. Then the sentence that names the one number that forced the design.
